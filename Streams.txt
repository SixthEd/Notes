When you run await stream.write(' 1 '), Node.js actually does not wait to build up a buffer.

Instead, it takes that tiny string, converts it to a binary buffer immediately for that specific piece of data, and instantly fires a system call to the OS. Because you have await there, the entire loop freezes, waits for the hard drive to reply "Got it!", and only then moves to i = 2.

[Loop i=1] ──> Create tiny buffer ──> System Call ──> (Wait for Disk)
[Loop i=2] ──> Create tiny buffer ──> System Call ──> (Wait for Disk)
... Repeated 1,000,000 times

2. The Stream Approach (Internal Buffering)

When you use a stream, your mental model is 100% correct. Node.js manages an internal buffer queue in V8 memory (RAM) that defaults to a highWaterMark of 16 KB for strings/buffers.

    Step 1: You call stream.write(' 1 '). Node puts it in the internal 16 KB buffer. The loop doesn't wait; it immediately jumps to i = 2.

    Step 2: This repeats rapidly in RAM until the accumulated strings hit that 16 KB limit.

    Step 3: Once full, Node.js takes that entire 16 KB chunk of data, makes one single system call, and flushes it to the disk all at once.

[Loop 1 to 2000] ──> Fill Internal 16KB Buffer (Ultra Fast RAM)
                               │
                       [Buffer is Full]
                               │
                               ▼
               1 Single System Call ──> Write 16KB to Disk

Why this matters for speed

A single 16 KB write takes almost the exact same amount of OS overhead as a 3-byte write. By grouping them into 16 KB chunks, you are reducing the number of operations from 1,000,000 down to roughly 400-500 system calls. That is why it feels instantaneous compared to the individual loop!

When you use stream.end(buff): It send and flushes that last buffer, closes the stream, and tells the system, "I am completely done. Do not expect any more data."

When you DON'T use stream.end(): The event loop still flushes that last data so it isn't lost, but the stream stays open, effectively saying, "I am empty right now, but I am still waiting and asking for more writes."

Initialization: You call fs.createReadStream('file.txt'). Node.js allocates a chunk of memory (the internal buffer) with a default highWaterMark capacity of 64 KiB.

The Fill Stage: Nodejs makes a low-level system call to read the file. It pulls the raw binary data from the disk and fills up that 64 KiB buffer.

The 'Data' Event (Flowing Mode): The moment you attach .on('data', ...), the stream kicks into gear. It wraps the binary data from the buffer into a Node.js Buffer object and emits it.

The Clear & Repeat Stage: Once that chunk is emitted to your listener, that space in the internal buffer is cleared out, and Node.js immediately goes back to the disk to read the next 64 KiB. This loop repeats until the end of the file (EOF) is reached.

	The moment your code enters that if(this.chunksSize > this.writableHighWaterMark) block and fires fs.write(), your custom stream becomes busy.

	Because fs.write() is an asynchronous operation, the callback() won't be executed until the hard drive finishes physically writing that concatenated buffer. While the hard drive is spinning and doing its 
	job, the stream's state is locked as "busy."
	
	Here is the exact sequence of events during that specific moment:
	The Timeline of the "Busy" State

	    The Threshold is Crossed: You call stream.write(). Your custom this.chunksSize goes over 1600.

	    The Async Trigger: Your code executes fs.write(this.fd, Buffer.concat(this.chunks), ...).

	    The Lock: Because you have not called callback() yet, Node.js marks this stream as busy.

	    Incoming Data Diverted: While fs.write is running in the background, if you call stream.write() again from your script, Node.js says: "Wait, _write is currently busy writing a massive concatenated 
	    chunk to the disk. I cannot pass this new data to _write yet."

	    Internal Buffer Fills Up: Node.js takes those incoming chunks and parks them inside its own hidden internal buffer.

	What happens when fs.write finishes?

	Eventually, the disk finishes writing, and the fs.write callback triggers:
	JavaScript

	this.chunks = [];
	this.chunksSize = 0;
	++this.writeCount;
	callback(); // <--- THE UNLOCK

	The moment that callback() is fired:

	    Node.js marks the stream as not busy.

	    Node.js looks at its internal buffer, sees the chunks that piled up while the disk was busy, pulls the first one out, and hands it to your _write() method.

	    If Node.js's internal buffer was completely filled up (causing stream.write() to return false) and is now completely emptied out by this process, Node.js will officially emit the "drain" event.

	To summarize your setup:

	You actually have two layers of queues acting like a funnel:

	    Your this.chunks array: Buffers data before it hits the disk, waiting for the size to cross 1600.

	    Node's Internal Buffer: Buffers data before it hits your _write method, but only during the brief window when fs.write is actively talking to your hard drive.
